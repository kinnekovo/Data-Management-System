## 一、项目目标

本项目旨在开发一个基于 MongoDB 的简易在线问卷系统，实现类似“问卷星”的基本功能。用户可以注册和登录账号，创建并管理自己的问卷，设置题目、发布问卷并通过链接分享给其他用户。填写者登录后可以完成问卷，创建者则能够查看问卷的填写情况和统计结果。

除了基本的问卷管理功能，本项目还需要支持单选、多选、文本填空和数字填空等题型，并允许创建者根据不同的题目设置答案校验和条件跳转规则。例如，根据用户的选择跳转到指定题目，或者限制多选题的选择数量、数字填空的取值范围等。这些规则需要能够由用户自行配置，而不是直接写死在程序中。



## 二、系统设计

### 2.1 总体架构

本项目采用前后端分离的三层架构，主要由 Vue 3 前端、FastAPI 后端和 MongoDB 数据库组成。

前端使用 Vue 3 和 Vite 开发，负责页面展示和用户交互，包括问卷编辑、填写和统计结果查看等功能。后端使用 Python 的 FastAPI 框架，通过 REST API 为前端提供数据和业务服务，同时负责用户身份验证、问卷管理、答案校验和条件跳转等逻辑。数据库采用 MongoDB，存储用户信息、问卷定义和填写记录。

前后端通过 HTTP 请求进行通信，开发环境下使用 Vite 代理转发 `/api` 请求。考虑到课程作业需要在助教电脑上运行，最终采用 Windows 本地部署方式，通过 PowerShell 脚本启动前后端服务，MongoDB 则作为本地数据库服务运行，不强制依赖 Docker。

### 2.2 功能模块设计

根据作业要求，系统主要分为用户管理、问卷管理、问卷填写和结果统计四个功能模块。

**（1）用户管理模块**

负责用户注册、登录和身份认证。系统使用 JWT 维护登录状态，密码经过 Argon2 哈希处理后保存到数据库中。同时，对问卷管理和统计接口进行权限检查，保证用户只能管理自己创建的问卷。

**（2）问卷管理模块**

用户登录后可以创建问卷，设置标题、说明、匿名填写和重复提交等选项，并添加单选、多选、文本填空和数字填空四种题型。

每道题目可以独立配置必答要求、答案校验条件和跳转规则。问卷创建完成后可以发布，并生成用于分享的访问链接。系统还支持设置截止时间和主动关闭问卷。为了避免修改题目后已有回答与问卷结构不一致，目前只允许在草稿状态下编辑题目，发布后冻结问卷定义。

**（3）问卷填写模块**

填写者通过分享链接进入问卷，登录后按照题目顺序或预先配置的跳转规则作答。前端根据当前答案计算下一道需要展示的题目，并在输入不符合要求时提示错误。

提交时，后端会重新检查答案的合法性和实际答题路径，而不是直接信任前端传来的结果。通过校验后，系统将本次填写保存到 MongoDB，同时根据问卷配置处理匿名展示和重复提交。

**（4）结果统计模块**

问卷创建者可以查看整份问卷或单道题目的统计结果。对于单选题，统计各选项的选择人数；对于多选题，统计每个选项被选择的次数；对于文本填空题，可以查看具体回答；对于数字填空题，可以计算平均值等统计指标。

统计结果由 MongoDB 中的实际填写记录生成，不需要在问卷中额外维护一份统计数据。此外，系统还支持分页查看原始答卷，方便创建者检查具体的填写情况。

### 2.3 后端分层设计

在代码组织上，后端没有将所有逻辑集中写在 API 接口中，而是按照不同职责划分为以下几个部分：

| 目录           | 主要职责                                         |
| -------------- | ------------------------------------------------ |
| `api`          | 定义接口，接收请求并返回结果                     |
| `schemas`      | 定义请求和响应的数据结构，完成基础数据校验       |
| `services`     | 实现问卷管理、条件跳转、答案校验和统计等业务逻辑 |
| `repositories` | 封装 MongoDB 的增删改查操作                      |
| `db`           | 管理数据库连接、集合 Schema 和索引               |
| `core`         | 管理系统配置、身份认证和通用功能                 |

这样的划分主要是为了减少不同功能之间的耦合。例如，问卷提交时，API 层负责接收答案，Service 层负责判断答题路径和校验规则是否满足要求，Repository 层则负责将合法的填写记录保存到 MongoDB。

由于作业第二阶段还需要根据新需求修改系统，将业务逻辑和数据库操作分开，也能减少后续修改对其他模块的影响。

### 2.4 主要业务流程

整个系统的使用过程可以分为问卷创建、问卷填写和结果查看三个环节。

首先，问卷创建者注册并登录系统，新建问卷后添加题目，配置选项、校验条件和跳转规则。完成编辑并通过发布检查后，系统将问卷状态改为已发布，创建者可以复制链接分享给其他用户。

填写者通过链接访问问卷并登录，系统根据其回答逐步展示后续题目。填写完成后，前端将答案提交至后端，由后端再次进行校验，确认不存在遗漏的必答题、非法选项或错误的跳转路径后，再将填写记录写入数据库。

最后，问卷创建者进入统计页面，后端通过 MongoDB 聚合查询生成各题的统计结果，并返回给前端展示。

通过以上设计，系统将问卷的创建、发布、填写和统计连接起来，形成了一个相对完整的业务流程。各模块之间通过明确的接口交互，也为第二阶段的功能调整保留了一定的空间。



## 三、MongoDB 数据库设计

### 3.1 数据模型设计

本项目使用 MongoDB 存储全部业务数据，数据库名称为 `survey_system`。在设计数据库时，主要需要考虑三类数据：用户信息、问卷定义和填写记录。

这三类数据之间的关系比较明确：一个用户可以创建多份问卷，一份问卷可以被多个用户填写，而一个用户也可以提交多份不同问卷的答卷。因此，我将数据划分为 `users`、`surveys` 和 `responses` 三个集合。

| 集合        | 主要内容                                     | 与其他集合的关系                                       |
| ----------- | -------------------------------------------- | ------------------------------------------------------ |
| `users`     | 用户名、密码哈希、注册时间                   | 一个用户可以创建多份问卷，也可以提交多份答卷           |
| `surveys`   | 问卷基本信息、题目、选项、校验配置和跳转规则 | 通过 `owner_id` 关联创建者                             |
| `responses` | 问卷 ID、填写者 ID、答案、提交时间           | 通过 `survey_id` 和 `respondent_id` 分别关联问卷与用户 |

其中，集合之间使用 MongoDB 的 `ObjectId` 进行关联，但问卷内部的题目、选项和跳转规则则直接嵌入 `surveys` 文档中。

对于问卷定义，用户打开问卷时通常需要同时读取所有题目、选项和规则。如果将这些内容分别存放，就需要多次查询或关联操作。因此，我将它们统一保存在 `surveys.questions` 数组中，一次查询就能获取完整的问卷结构。而且，不同题型可以有不同的 `validation` 配置和跳转规则，也比较适合 MongoDB 灵活的文档结构。

但填写记录不能采用相同的方式。一份问卷可能被很多人填写，如果每次提交都往问卷文档中追加答案，文档会不断增大，多人同时提交时还需要频繁修改同一条记录。因此，系统使用独立的 `responses` 集合保存答卷，每次提交生成一条新文档。

### 3.2 具体文档结构

**（1）用户文档** `users`

用户集合的结构比较简单，主要包含以下字段：

| 字段            | 含义                         |
| --------------- | ---------------------------- |
| `_id`           | MongoDB 自动生成的用户 ID    |
| `username`      | 用户名                       |
| `password_hash` | 使用 Argon2 加密哈希后的密码 |
| `created_at`    | 注册时间                     |

系统不会直接保存明文密码。用户登录时，后端根据用户名查询对应的密码哈希，再验证用户输入的密码。

**（2）问卷文档** `surveys`

问卷文档是整个系统中结构最复杂的部分，主要分为问卷基本信息和题目定义两部分。

问卷基本信息包括：

| 字段                         | 含义                           |
| ---------------------------- | ------------------------------ |
| `_id`、`owner_id`            | 问卷 ID 和创建者 ID            |
| `slug`                       | 用于生成问卷分享链接的唯一标识 |
| `title`、`description`       | 问卷标题和说明                 |
| `status`                     | 问卷状态：草稿、已发布或已关闭 |
| `allow_anonymous`            | 是否匿名展示填写者身份         |
| `allow_multiple_submissions` | 是否允许同一用户重复提交       |
| `expires_at`                 | 问卷截止时间                   |
| `questions`                  | 包含全部题目的数组             |
| `definition_version`         | 问卷定义版本号                 |
| `created_at`、`updated_at`   | 创建与修改时间                 |

其中最重要的是 `questions` 数组。每道题目采用相同的基本结构，包含以下字段：

| 字段         | 含义               |
| ------------ | ------------------ |
| `id`         | 题目的唯一标识     |
| `type`       | 题目类型           |
| `title`      | 题目内容           |
| `required`   | 是否必答           |
| `options`    | 单选或多选题的选项 |
| `validation` | 答案校验条件       |
| `rules`      | 条件跳转规则       |

例如，一道要求选择 1～2 个选项的多选题，可以表示为：

```json
{
  "id": "q2",
  "type": "multiple_choice",
  "title": "你使用过哪些编程语言？",
  "required": true,
  "options": [
    {"id": "a", "label": "Python"},
    {"id": "b", "label": "Java"},
    {"id": "c", "label": "C++"}
  ],
  "validation": {
    "min_selections": 1,
    "max_selections": 2
  },
  "rules": []
}
```

这里的 `options` 决定前端展示哪些选项，`validation` 决定答案需要满足什么条件，`rules` 则决定回答后是否需要跳转。不同题型使用相同的基本结构，但可以有不同的配置内容。

另外，题目和选项都使用独立 ID，而不是直接用数组下标表示。这样即使用户在草稿状态下调整题目顺序，也不会因为位置变化而使原来的跳转规则失效。

**（3）答卷文档** `responses`

填写记录不保存整份问卷，而是通过问卷 ID 关联对应的定义，主要字段如下：

| 字段                 | 含义                                           |
| -------------------- | ---------------------------------------------- |
| `survey_id`          | 所属问卷的 ID                                  |
| `respondent_id`      | 填写者的用户 ID                                |
| `definition_version` | 提交时对应的问卷版本                           |
| `answers`            | 实际提交的答案数组                             |
| `submitted_at`       | 提交时间                                       |
| `submission_guard`   | 用于限制重复提交的标识，仅在禁止重复提交时设置 |

例如，一份包含单选、多选和数字题的答卷可以表示为：

```json
{
  "survey_id": "问卷ObjectId",
  "respondent_id": "用户ObjectId",
  "definition_version": 1,
  "answers": [
    {"question_id": "q1", "value": "a"},
    {"question_id": "q2", "value": ["a", "b"]},
    {"question_id": "q3", "value": 90}
  ],
  "submitted_at": "提交时间"
}
```

这里为了便于阅读，用文字代替了实际的 ObjectId 和日期对象。真实数据中，这些字段使用对应的 MongoDB BSON 类型。

不同题型的答案使用不同的数据形式：单选题保存一个选项 ID，多选题保存选项 ID 数组，文本题保存字符串，数字题保存数值。

需要说明的是，匿名填写并不等于不需要登录。系统仍然保存 `respondent_id`，以便进行身份验证和重复提交检查；但当问卷设置为匿名时，创建者查看答卷的接口不会返回填写者身份信息。

### 3.3 Schema 与索引设计

除了确定文档结构，项目还在 `backend/app/db/schema.py` 中定义了 MongoDB 的 `$jsonSchema`，对数据库中保存的数据进行基本约束。

例如，用户文档必须包含用户名、密码哈希和注册时间；问卷状态只能是 `draft`、`published` 或 `closed`；`responses.answers` 必须是数组。

不过，数据库 Schema 主要负责字段类型和基本结构的检查。对于“多选题最少选择数不能大于最多选择数”“跳转目标题必须排在当前题之后”等涉及业务语义的规则，仍然由后端 Service 层检查。

为了保证数据唯一性并优化常用查询，系统还建立了以下五个索引：

| 索引                                 | 类型         | 作用                               |
| ------------------------------------ | ------------ | ---------------------------------- |
| `users.username`                     | 唯一索引     | 防止用户名重复，支持登录查询       |
| `surveys.slug`                       | 唯一索引     | 保证问卷分享链接唯一               |
| `surveys.owner_id + created_at`      | 复合索引     | 按创建者查询问卷，并按创建时间排序 |
| `responses.survey_id + submitted_at` | 复合索引     | 查询某份问卷的填写记录，支持分页   |
| `responses.submission_guard`         | 唯一部分索引 | 防止同一用户并发重复提交           |

最后一个索引主要用于解决重复提交问题。对于不允许重复填写的问卷，后端根据问卷 ID 和用户 ID 生成固定的 `submission_guard`。即使两个提交请求同时到达，数据库的唯一索引也只允许其中一条记录成功写入。对于允许重复填写的问卷，则不设置这个字段。

总体来看，这种设计将相对固定的问卷定义和持续增长的填写数据分开，同时利用嵌入文档存储联系紧密的题目和规则，比较适合本项目的查询和写入需求。



## 四、题目校验与跳转实现

问卷系统除了保存题目，还需要根据用户的配置判断答案是否合法，以及回答后应该进入哪道题。因此，我将这部分逻辑分为三个环节：**发布前检查题目配置、填写时校验答案、根据答案计算跳转路径。**

### 4.1 问卷发布前的配置校验

创建者在编辑问卷时，可以添加题目、设置选项和校验条件，也可以配置题目之间的跳转关系。但这些配置本身也可能存在错误，因此系统会在问卷发布前进行一次完整检查。

主要检查以下内容：

- 问卷是否至少包含一道题，题目和选项 ID 是否重复。
- 单选、多选题是否至少包含两个选项。
- 校验条件是否合理，例如最小选择数不能大于最大选择数。
- 跳转条件是否与题型匹配，例如文本题不能配置数字大小比较。
- 跳转的目标题是否存在，是否位于当前题之后。
- 同一道题的跳转规则是否存在重复优先级。

如果检查不通过，后端会返回具体的错误信息，要求创建者修改后再发布。

这样可以尽量在问卷被填写之前发现配置问题，而不是等到用户作答时才出现无法跳转或无法提交的情况。

### 4.2 答案校验

对于填写者提交的答案，系统根据题目类型及 `validation` 字段进行校验，而不是针对每一份问卷单独编写判断逻辑。

四种题型对应的校验方式如下：

| 题型     | 答案形式     | 校验内容                                     |
| -------- | ------------ | -------------------------------------------- |
| 单选题   | 单个选项 ID  | 选项是否存在、是否必答                       |
| 多选题   | 选项 ID 数组 | 选项是否合法、有无重复、选择数量是否满足限制 |
| 文本填空 | 字符串       | 是否必答、最小长度、最大长度                 |
| 数字填空 | 数值         | 是否必答、最小值、最大值、是否必须为整数     |

例如，对于一道“年龄”数字题，可以设置：

```json
{
  "type": "number",
  "required": true,
  "validation": {
    "min_value": 0,
    "max_value": 120,
    "integer_only": true
  }
}
```

这样用户输入 `20` 时可以通过校验，输入 `130` 或 `20.5` 时则会提示错误。

这里需要区分两种校验：前端校验主要是为了及时提示用户，避免填写完才发现错误；后端校验则负责保证最终保存的数据合法。因为用户可以绕过前端直接发送 API 请求，所以提交时不能只依赖前端的检查结果。

实际实现中，后端先利用 Pydantic 检查请求的基本结构，再通过 `services/validation.py` 中的 `validate_answer()` 根据题型检查答案内容，只有通过校验的答案才能进入后续保存流程。

### 4.3 条件跳转规则

条件跳转是本项目比较重要的功能。与普通问卷按顺序展示所有题目不同，系统需要根据当前题目的回答，决定下一道应该展示什么。

为了让创建者自行配置跳转，系统将规则保存在题目的 `rules` 数组中。每条规则包含四个字段：

| 字段                 | 含义                         |
| -------------------- | ---------------------------- |
| `priority`           | 规则优先级，数字越小越先检查 |
| `operator`           | 条件运算符                   |
| `value`              | 用于匹配答案的值             |
| `target_question_id` | 条件满足时跳转到的题目 ID    |

例如，一份调查问卷包含：

- Q1：你是否有编程经验？（A：有；B：没有）
- Q2：你为什么想学习编程？
- Q3：你使用过哪些编程语言？
- Q4：你对自己编程水平的评分？

希望在 Q1 选择 A 时跳过 Q2，直接进入 Q3；选择 B 时则正常进入 Q2。

这时，可以在 Q1 中设置以下规则：

```json
{
  "priority": 1,
  "operator": "eq",
  "value": "a",
  "target_question_id": "q3"
}
```

当填写者选择 A 时，系统匹配到这条规则，直接展示 Q3；如果选择 B，没有匹配到规则，就按照原来的题目顺序进入 Q2。

除了单选题，系统还支持多选和数字题的条件跳转：

| 题型 | 运算符                         | 含义                                 |
| ---- | ------------------------------ | ------------------------------------ |
| 单选 | `eq`                           | 答案等于指定选项                     |
| 多选 | `contains_any`                 | 至少选择指定选项中的一项             |
| 多选 | `contains_all`                 | 同时包含所有指定选项                 |
| 数字 | `eq`、`gt`、`gte`、`lt`、`lte` | 等于、大于、大于等于、小于、小于等于 |

例如，对于一道包含 A、B、C 三个选项的多选题，如果希望用户同时选择 A 和 B 才触发跳转，可以设置：

```json
{
  "priority": 1,
  "operator": "contains_all",
  "value": ["a", "b"],
  "target_question_id": "q5"
}
```

而如果希望选择 A 或 B 中任意一项就触发跳转，只需将运算符改成 `contains_any`。

系统按 `priority` 从小到大检查规则，找到第一条满足条件的规则后跳转；如果没有任何规则匹配，就进入下一道题。为了简化第一阶段的实现并避免循环跳转，目前只允许跳向后面的题目。

### 4.4 答题路径的计算与检查

有了条件跳转后，还需要解决一个问题：**哪些题目才是真正需要填写和校验的？**

还是以上面的问卷为例，如果 Q1 选择 A 后直接跳到 Q3，那么 Q2 即使设置了必答，用户也不应该被要求填写。

因此，系统不能简单地遍历整份问卷，检查所有必答题是否都有答案，而是需要先计算实际答题路径。

前端在用户填写时，根据当前答案动态决定下一道题目。如果用户返回修改之前的答案，前端会重新计算路径，并清除不再属于当前路径的旧答案。

但仅靠前端处理还不够。系统在后端实现了 `replay_path()`，用于在提交时重新计算完整的答题路径，主要过程如下：

1. 从问卷的第一道题开始。
2. 获取当前题目的答案，并按照对应题型进行校验。
3. 如果当前题目有答案，就按优先级检查跳转规则。
4. 如果匹配到规则，则进入指定题目；否则进入下一道题。
5. 重复上述过程，直到问卷结束。
6. 检查提交数据中是否包含未知题目、重复题目或实际路径之外的答案。

例如，用户在 Q1 选择 A 后，正常路径应该是 Q1 → Q3 → Q4。

此时即使 Q2 是必答题，也不需要提供 Q2 的答案；反过来，如果用户通过修改 HTTP 请求，额外提交了 Q2 的答案，后端就会判断这道题不属于实际答题路径，拒绝本次提交。

也就是说，前端负责根据规则展示题目，后端负责重新计算并确认答案的合法性。这样既能保证填写体验，也能避免用户绕过规则提交不符合要求的数据。



## 五、问卷提交与结果统计

### 5.1 问卷提交流程

填写者通过问卷分享链接进入填写页面，登录后即可开始作答。完成填写后，前端将答案列表发送到后端提交接口。

后端收到请求后，并不会立即保存，而是依次完成以下检查：

1. **检查问卷状态。** 确认问卷已经发布，没有被关闭，也没有超过截止时间。
2. **检查答题路径。** 根据问卷中的跳转规则重新计算用户应该访问的题目。
3. **校验答案。** 检查实际路径上的必答题、选项和输入内容是否符合要求。
4. **处理重复提交。** 根据问卷是否允许重复填写，决定是否生成 `submission_guard`。
5. **保存答卷。** 将通过校验的答案、问卷 ID、填写者 ID 和提交时间写入 `responses` 集合。

保存时只记录经过校验的有效答案，不会将被跳过题目的无效回答一起存入数据库。

如果问卷不允许重复填写，同一用户再次提交时，MongoDB 的唯一索引会阻止重复记录插入，后端返回相应的错误提示。

这样一来，每条保存的答卷都对应一次合法提交，后续统计也能够直接基于这些记录进行。

### 5.2 统计结果的生成

系统没有在 `surveys` 中额外保存每道题的选择次数，而是直接从 `responses` 中读取已经提交的答案，通过 MongoDB 的 Aggregation Pipeline 生成统计结果。

这样可以避免同时维护原始答卷和统计计数两份数据。当有新答卷提交时，再次查询就能得到更新后的结果。

具体而言，不同题型采用不同的统计方式：

| 题型     | 统计内容                         | MongoDB 实现方式                        |
| -------- | -------------------------------- | --------------------------------------- |
| 单选题   | 各选项选择人数、回答总人数       | 按选项 ID 分组，通过 `$group` 计数      |
| 多选题   | 各选项被选择的次数、回答人数     | 先用 `$unwind` 展开选项数组，再分组计数 |
| 文本填空 | 回答人数、具体填写内容           | 按题目筛选记录，具体内容分页查询        |
| 数字填空 | 回答人数、平均值、最小值、最大值 | 使用 `$avg`、`$min`、`$max` 聚合        |

这里以多选题为例说明。假设三名用户分别选择了：

- 用户 1：A、B
- 用户 2：B、C
- 用户 3：A、C

在数据库中，多选答案保存为数组。统计时先使用 `$unwind` 将每份答案中的选项展开，再按照选项 ID 分组计数，最终得到：

| 选项 | 被选择次数 |
| ---- | ---------- |
| A    | 2          |
| B    | 2          |
| C    | 2          |

需要注意，这道题的回答人数是 3，而所有选项的选择次数之和是 6，两者并不相同。

### 5.3 条件跳转对统计的影响

由于系统支持跳转，并不是所有填写者都会经过全部题目，因此每道题的回答人数可能不同。

例如，一份包含 Q1～Q4 的问卷中，Q1 选择 A 时直接跳到 Q3，选择 B 时正常进入 Q2，之后都继续回答 Q3 和 Q4。

假设有两名用户提交了问卷：

| 用户   | 实际答题路径      | Q4 评分 |
| ------ | ----------------- | ------- |
| 用户 1 | Q1 → Q3 → Q4      | 20      |
| 用户 2 | Q1 → Q2 → Q3 → Q4 | 40      |

那么，整份问卷的提交次数是 2，但 Q2 只有 1 人实际回答，Q3 和 Q4 都有 2 人回答，Q4 的平均分为：(20+40)/2=30。

因此，统计时不能直接将问卷总提交次数作为每道题的回答人数。系统会先筛选实际包含该题答案的填写记录，再进行对应的聚合计算。

最后，系统提供整份问卷统计和单题统计两种查询方式，创建者既可以查看各题的汇总结果，也可以分页查看原始答卷。对于设置为匿名的问卷，查看答卷时不会返回填写者身份信息。

目前采用实时聚合的方式，主要是考虑到课程项目的数据规模较小，实现也比较直接。如果后续问卷数量和填写记录大幅增长，再考虑增加统计缓存等优化方式。

## 八、开发中遇到的问题

### 8.1 条件跳转与必答校验之间的冲突

实现条件跳转时，我发现一个需要特别处理的问题：如果问卷中存在必答题，但用户通过跳转规则跳过了这道题，那么提交时是否还需要检查它？

例如，一份问卷共有五道题，Q2 和 Q3 都是必答题，但用户在 Q1 选择某个选项后直接跳转到 Q4。如果简单地遍历所有题目进行必答检查，那么用户就无法提交问卷，显然不符合条件跳转的预期。

我认为这里应该区分“问卷中有哪些题目”和“用户实际需要回答哪些题目”。因此，必答校验不能只根据题目本身的配置进行判断，还必须结合用户的实际答题路径。最终采用的方案是：前端根据答案动态计算需要展示的题目，后端在提交时重新执行跳转规则，只校验当前路径上的必答题，同时拒绝不属于该路径的答案。

另外，当用户返回修改前面的答案时，后续路径也可能发生变化，因此前端还需要清除旧分支中已经填写的内容，避免把无效答案一起提交。

这个问题也影响了统计功能。对于存在条件跳转的问卷，不同题目的实际回答人数可能不同，因此统计时需要根据每道题真正收到的有效答案计算，而不能直接使用整份问卷的提交人数。

### 8.2 问卷发布后如何保证数据的一致性？

另一个需要考虑的问题是，问卷发布并产生填写记录后，如果创建者继续修改题目或选项，之前保存的答案应该如何处理？

例如，某道单选题原本有 A、B、C 三个选项，已有用户选择了 C。如果创建者之后删除选项 C，那么历史答案就可能无法正确对应当前问卷结构，统计结果也会产生歧义。

考虑到第一阶段并不要求支持复杂的问卷版本管理，我最终采用了比较简单的处理方式：问卷在草稿状态下可以自由编辑，发布前进行完整的题目与规则检查，发布后则冻结问卷结构，不再允许修改题目定义。

此外，对于不允许重复填写的问卷，最初容易想到的做法是先查询用户是否提交过，再决定是否保存。但如果同一个用户同时发起两次请求，两次查询都可能发现没有历史记录，最终产生重复提交。因此，除了在业务层进行检查，还使用 MongoDB 的唯一部分索引限制重复记录，避免并发情况下出现问题。

这些问题让我意识到，问卷系统虽然看起来功能比较简单，但不同功能之间其实存在不少关联。设计时不能只考虑某个功能能否单独运行，还需要考虑它会不会影响已有数据，以及多个功能组合使用时是否仍然符合预期。
